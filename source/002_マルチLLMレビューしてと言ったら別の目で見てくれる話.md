# 第4話 スキル物語 「マルチLLMレビューして」と言ったら別々の目で見てくれる話

## いつ困る？
設計を書き上げた瞬間「これでいいのか不安」になる。自分の目で3回読み直しても、慣れで見落として怖い。同じLLMに「ツッコんで」と頼んでも、同じ死角を同じように見落とす。堅牢に見せたいのに、別の視点が足りない——完成前の判断が甘くなる瞬間、毎回の不安が膨らむ。

## こう言うと起こること
「マルチLLMレビューして」「複数LLMでレビュー」を CC に投げる。裏側では別々の LLM（WSL CLI 版では既定で MiniMax と Gemini、「各LLMに」と付け加えれば OpenRouter の無料枠も加わって3機）が**互いに一切相手の回答を見ずに**同じ設計を叩く。レビュアーの間で引用の奪い合いは起きず、それぞれ独立に欠陥を見つける。そして CC がその指摘を「当初目的」という唯一の基準で取捨選択して、構造を保ったまま統合した改訂案を作る。直交した目で見た結果が、1つの解答として返ってくる。

## 何が変わるか
「同じ LLM の独り言」では届かなかった死角を、複数モデルが独立に埋めてくれる。1ラウンドで2視点、3機モードで3視点が同じコストでそろう。「思ったより深掘りが出た」という驚きが、設計の底力を一段上げてくれる。出力された改訂案は面接資料・設計書・外向き文面など、判断の重さが要る全てのもののリハーサルとして使える——発表前に「別々の目」を通す習慣が身につく。

### 仕組み

- 同じプロンプトを2〜3機のLLMに**並列独立**で送出し、各自の指摘のみを集める
- 統合はCC自身が「LLM内のステップ」として行うため、外部LLMを追加呼び出ししない（独立性命題を維持）
- 8ステップ（JSON抽出→severity正規化→Fact Check→ペルソナ切替→3 tier分類→メタ中断→競合調停→統合）で改訂案を作る
- 統合の最終段で「もう一度各LLMでレビューしますか？」と添える Step9 が2026-09-02 追加（収束自己判定の封じ）

### lite（multi-llm-review-lite）との使い分け

- 「軽く」「サクッと」が発話に入れば lite（箇条書きツッコミ・会話内完結・改訂案なし）
- 「しっかり」「3機で」「改訂案が欲しい」は本スキル normal モード
- 曖昧なら迷う必要はなく CC が確認する

### 注意点

- レビュー対象本文はプロンプトにインラインで貼る（ファイルパス渡しではない・LLMはテキスト生成APIでファイルを読めないため）
- 「ゼロ件」「見つからない」等の断定をするときは再検索プロトコルが必要（`grep -rln` head無し）
- 機密情報のレビューは LLM 送信前にマスク・リスク警告が出る
