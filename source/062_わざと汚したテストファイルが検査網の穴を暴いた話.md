# わざと汚したテストファイルが、検査網の穴を暴いた話

## 困ったこと
設定ファイルを安全な場所に自動で複製する仕組みを作った直後のこと。出来上がった直後に、自動で動く安全点検が「このままだと秘密情報が漏れる危険を止められません」と、重要度の高い指摘を2つも持ってきました。出来たばかりの仕組みへの容赦ない指摘でしたが、内容を読むとどちらも正当なものでした。1つは「問題が起きた後に記録を残すだけで、肝心の保存を止められていない」、もう1つは「ある種の設定の隠し場所の掃除が抜けている」というものです。

## どう解決したか
指摘どおりに直すだけでは終わらせず、仕組みの考え方を変えました。それまでの「問題を見つけたら記録に残す」から、「問題を見つけたら複製そのものを消して、保存の入口から締め出す」方式へ。加えて、設定の隠し場所を値のパターンで探すのではなく、隠し場所そのものを丸ごと掃除する構造的な防御も足しました。そして最後に、わざと秘密情報を混ぜた「汚れたテストファイル」6個を作って、検査網に通してみました。結果は4個が正しく削除されたものの、検証を進めるうちに思いがけないことが判明します。ある書き方の秘密情報が、**1個も検知できていなかった**のです。

## 何が変わったか
見つかった穴の正体は、検査網のパターンが「特別な書き方をされた秘密情報」を見落とすという、地味で深刻なものでした。しかもそれは、数日前に実際に起きた事故とまったく同じ形をしていました。本番のファイルがきれいに見えていたからと言って、検査網が正しく動いている証明にはならない——動かない毒を混ぜて確かめて、初めて穴が見える。この経験から「確認した」ではなく「わざと汚したファイルで実証した」を、受け入れの条件として日誌に書き留めました。穴が見つかったのは不幸でしたが、直後に実証テストを仕掛けたのは幸いでした。見つけていなければ、同じ形の事故がいつか再発していました。

背景: `sync-claude-md.sh` 3.8（settings.json等5ファイルをSSOTへ副本同期する仕組み）の初回実装直後に security-guidance plugin の post-commit review から HIGH 指摘2件を受領した対応。

指摘と対応: ①**post-write-detection-only** — 検出をwrite後のみでWARNログ止めでは git commit を阻止できない → **PRE-check**（cp/rsync前に源ファイルを検査し、機密があれば同期中止）+ **POST-check fail-closed 化**（副本検査で機密検出時に `rm -f` で副本を物理削除し commit 候補から消滅）。②**incomplete-sanitization** — `mcpServers[].env`/`headers` の構造的クリアが無い → 値パターン非依存の構造的サニタイズを追加（実績ある `sync-settings-to-example.sh` と同ロジック・当初の YAGNI 判断を撤回）。

実バグ: POST-check の bash grep パターン `(['\"]?)[A-Za-z0-9._=-]{15,}` が、JSON 文字列内のエスケープ形式 `TOKEN=\"value\"` を取りこぼす（`TOKEN=` 直後がバックスラッシュで `['\"]?` に非合致）。2026-07-29 の TOKEN 露出事故（`Bash(TOKEN=\"value\")`）と同一形式。修正は `=\\?[\'\"]?...` への optional backslash 追加。

検証: 合成テスト6ファイル（クリーン2+汚染4）で「汚染4件全削除・クリーン2件残存」を実証（修正前は TOKEN= エスケープ形式のみ検出漏れ）。本番の settings.local.json に混入が無かったのは偶然で、検知ロジック自体は壊れていた。
