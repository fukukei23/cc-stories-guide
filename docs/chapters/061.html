その作業は無理と決めつける前に引き出しを開けよう

困ったこと

睡眠データを記録する小さなアプリ（Nemly）を作っていた時のこと。最後の検査で「本物のスマホの画面で動かしてみる」段階に来た時、この作業を担うAIはこう結論づけました。「スマホやエミュレータはここからは操作できません。人間の皆さん、お願いできますか」と。ところが相手にされたふくけいは、たった一言返してきました。「本当に？理由は？」。この一言が、間違った結論をひっくり返すことになりました。

どう解決したか

言われた通り、手元をちゃんと調べてみました。すると驚くことに、スマホを動かすための道具一式（開発環境・昔作ったテスト用の設定まで）が、最初から手元の開発環境の中に揃っていたのです。何も無いと思い込んでいた引き出しを開けたら、道具箱ごと入っていました。そこからは順調で、仮想のスマホを起動し、作ったアプリを入れ、本物の睡眠データを読み込ませ、画面の写真を撮って自分の目で確認するところまで、たった一人で完遂できました。最初の「無理」は、引き出しを開けずに決めつけただけだったのです。

何が変わったか

同じ失敗は前にもありました。画像を見せてもらう時、「ここからは見えない」と外部の道具に頼み込んだら、後から「それ、自分で見えたのに」と気づいたのです。二度目なので、今回は「引き出しを先に開ける」という行動のルールを日誌に書き留めました。加えて、その道具箱の置き場所と使い方を正式な手引書として登録したので、次に同じ壁にぶつかった他の作業仲間も、迷わずに済みます。「できない」と言う前に、まず開けて確認する。地味ですが、これだけで無駄なお願いと手戻りが一つ減ります。

背景: 睡眠データ判定アルゴリズム（sleep-algorithm・クリーンルーム実装）を Expo アプリに組み込む作業で、実機検証段階に到達した際の誤断定と訂正。

誤断定の実体: WSL2 は USB デバイスを直接握れない（adb devices が空になる）ため「スマホ/エミュレータは操作できない」と一般化して断定した。実際には: ①WSL 内に Android SDK フルセット（emulator・既存 AVD・adb・build-tools・NDK）が実在 ②/dev/kvm が使用可能 ③エミュレータの headless 起動（-no-window）が成功（Android 15）④expo prebuild + Gradle による WSL 内ビルドが成立。

実施した検証: node:sqlite（Node 24 内蔵）で SQL 契約 10 項目を検証（rollback 時の部分保存不発生・UNIQUE 制約の first-wins・lastInsertRowid の型・FK 削除順序・保存→再読込照合）。release ビルド時に Node crypto の解決失敗を検出し、metro.config.js で空モジュールへ差し替え（テスト専用の FakeAdapter の require が本番バンドルに紛れ込む問題）。E2E では実データ 1342 サンプルでスコア 67・REM 13%（原典 ~REM13% と一致）・覚醒 1%（原典 1% と一致）をスクショ目視で確認。

正典: SSOT の Android 検証ケイパビリティ文書（00_SYSTEM 配下・手順と制約を記載）。memory には「実測前に『できない』と断定しない」の行動ルールを記録。過去の同型事故（画像認識を外部委任した件）へのリンク付き。
