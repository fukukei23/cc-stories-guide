第73話 作業物語 1,680行の書き換えを36回の小分けと3人のAI合議で間違いゼロで終わらせた話

困ったこと

日記帳（作業の記録）に、ある言葉が1,680行も残っていた。「お客さま」という言葉だ。でもこの言葉、本当は主人（ふくけい）のことを指して書かれていた行がほとんど。全部「ふくけい」という名前に書き換えたい。

ところが話はそう簡単ではない。同じ「お客さま」でも、本当に客のことを指している行が60行ある。さらに、機械の設定文の中や誰かの発言を写した引用の中には、書き換えてはいけない行がある。全部まとめて一気に書き換えると、書いちゃいけない行まで書き換える事故が起きる。

1行ずつ人間が目で見て直すには日がかかる。かといってAIに一括でやらせると事故が出る。「早さ」と「安全」が両立しない見えた。

どう解決したか

36回に小分けした。1回は50行だけ。1回ごとに記録を残すので、もし何か起きても「どの回で起きたか」がすぐ分かる。

判定は3人のAIに合議させた。2票以上そろった行だけ自動で書き換え、**意見が割れた行は「迷い行」**として人間だけに聞く。さらに安全のため、「判定をしたAI自身が迷った行」は他の2人が一致していても迷い行に回すルールを足した。

最後の門は機械のチェック。「客を指す行が混ざっていないか」「行の並びがズレていないか」を書き換えの前に機械が確かめる。実際、最初の試し方に**「順番の番号」と「ファイルの中の行番号」を取り違える欠陥があり、客の行を書き換えてしまう案が出てきたが、この機械の門が適用の前に止めた**。

結果は約1,350行を書き換え、間違いゼロ。客の行を主人と書き換える逆転事故もゼロ。残りは機械が守る行（設定文・引用など）だけで、書き換えるべき行は無くなった。

何が学べるか

大きな書き換えは、**「少しずつ」「機械の門」「複数の判定者の合議」**の3つで安全にできる。危険な作業ほど、1回の変更を小さくして「どこで何が起きたか」を追える形にするのが近道だった。

パイプラインは6段: ①select_batch.py で決定論的に50行を抽出（コードブロック・引用・第三者は機械保護）→ ②3機判定（CC=flash ホスト内・MiniMax・Gemini の2票以上多数決・迷い行は人間裁定。CC が曖昧にした行は2票でも迷い行へ=安全側ルール）→ ③dry-run diff を人間承認 → ④blind audit（3行無作為照合）→ ⑤apply（行ズレ text 照合・第三者混入 assert）→ ⑥1バッチ1コミット。

  • 初版スクリプトのバッチ内連番とファイル内行番号の混同バグが「マルチユーザー化」を「マルチふくけい化」にする誤案を生成したが、dry-run＋blind audit＋混入 assert の3層で適用前に捕捉
  • 判定済み対象外行が pending に残り続けて未判定行を飛ばすドリフト問題は judged_skip.json の ledger 機構で解消（batch34 実測: 残156行のうち67行が判定済み→89行に収束して完走）
  • 教訓: git commit -- pathspec は staged を上書きする罠・| tail パイプで exit code を見間違いコミット消失2件（生 exit code 添付ルールの自らの違反を機械で再発見）

依存: 50_PROJECTS/呼称1680/（select_batch.py・apply_batch.py・judged_skip.json）。作った経緯: 呼称・主語ルール実装（08-29）で新規記録は対応済みだったが既存1,680行が放置されており、進め方は3機レビュー（triple）で「単価未確認で決めるな」指摘→バッチ1で両モデル実測比較→ふくけいが flash 続行を決定。
