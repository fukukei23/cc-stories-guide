バージョン番号ひとつで壊れる世界

物語

データベースに手を入れたのは、17 番目の朝のことでした。それまで数日かけて作っていたアプリが、壊れていたのです。画面は動く。ボタンも押せる。でもデータを更新して再起動すると元に戻る――つまり、保存の仕組みがあるはずなのに、毎回ゼロからが始まっているのです。

原因は意外にも簡単でした。最初の指示は「データは 1 番目のテーブルにすべて入れる」だけだったのです。テーブルを増やす必要が出てきたとき、古いデータを新しい場所へ移す手順をひとつしか用意していませんでした。この欠落は、履歴には記録されていません。

最初は「バージョン番号を 1 ずつ上げるだけでいい」という状態を続けていました。しかし、テーブルが 47 個を超えたあたりで、もう 1 番目から 2 番目までの間にしか間に合っていないと気づきました。案 B として書いた初歩的な方法は負債となり、将来essiveの都需要を考えると確実にひとつずつ狂っていくので、直ちに破棄しました。

調べるたびに、自分の設計が壊れていることが分かりました。設計レビューで 38 件、コード実装レビューで 36 件。そのうち 5 件は、「これを入れると計算できない」ほど致命的な内容でした。私は重大と書かれていた 5 件を、その場で修正しました。

設計を見直すと、要件を「移行、冪等性、予備手段、連続性、認証、記録」という 6 つの層に分けたことが、対話できるリズムを作りました。設計レビューでは、3 名が独立して「履歴テーブルがない」と指摘し、1 名の意見ではなく「構造が欠けている」証拠になったのです。

転機は観測でした。すべての数字が緑になりました（98 個）。しかし、私は慎重で、**「その数字はまだ実機で動いていない」**と理解していました。そのため、翌日に「実機で 0 から 1、2 へ 올라가는際に何が壊れるか」を書き残しました。

何が教訓だったか

  • 単独設計より複数設計：設計レビュー 38 件のうち、3 名が独立して同じ構造の欠落を指摘しました。「1 名の意見は意見、3 名の指摘は構造」。問題そのものを修正するのではなく、問題を提起できる構造にすることが正しい答えでした。
  • 「その場で発見したもの」を設計に入れる：レビューの重大 5 件は、その日のうちにテストケースとともにコードへ組み込みました。コメントとして残すのではなく、動くテストとして残すようにしました。
  • 早すぎる完了と未完の完了：テスト 98 件が緑になったことを終点にしない。「そのテストが実機で通る保証はない」ことを明記し、次の段階での最も明確な検証を戦場にします。

次の段階への持ち越し

次の段階では、このフレームワークが実機で動作するかを確認します。そこで初めて反証が可能になります。緑になった数字も、実機で壊れたなら正解ではなかったと分かります。

実装内容

  • src/lib/migration/migrations.ts — v1 migration オブジェクト + V1_CHECKSUM
  • src/lib/migration/migrationRunner.ts — schema_migrations テーブル + bootstrap + 連続性検証 + checksum 検証
  • src/lib/migration/sqliteAdapter.ts — PRAGMA 抽象化 + tableExists + runInTransaction

採用した設計（案A）

  1. adapter 層で PRAGMA を閉じ込める → expo-sqlite SDK の差し替え時に 1 ファイルで吸収
  2. schema_migrations テーブルで履歴管理 → 仕様 13 の重要要件
  3. bootstrap AND 条件（user_version>=1 && 物理テーブル存在） → 既存 DB の誤注入を防止
  4. 1 migration = 1 transaction → DDL 失敗時のロールバック

却下した案

  • 案B：PRAGMA 文字列を直接 migrationRunner に埋め込む → 実際の expo-sqlite 統合時に全面的な書き直しが必要になる負債
  • 案C：better-sqlite3-wasm で実 SQL エンジンを使用する → Day 4 では過剰（偽物テストの水準で TDD は可能）

検証結果

  • テスト 98 件が緑・tsc=0・coverage 88.88%
  • 設計レビュー 38 件中 11 件を採用、コードレビュー 36 件中、重大 5 件を即修正

残課題（Day 5 以降）

  1. autoBackup の実実装
  2. 実 expo-sqlite 統合テスト（simulator または EAS Build で v0→v1→v2 へ昇格し、冪等再実行を確認）
  3. migration 失敗時の UX
  4. PR2：SQLiteRepository の切替
