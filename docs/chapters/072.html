第72話 作業物語 「フックが動かない」と言って設定を直しかけたら、原因の読み違えだった話

困ったこと

盾（安全装置）がある。“不要な作業を防いでくれる仕組み”だ。これは「どの操作で反応するか」という合図の指定をみて動く。

問題は、その盾が特定の操作のとき一切反応しなくなっていたこと。「空の合図指定は効かない」「合図を全部に広げれば動く」という2つの説を立て、どちらも外していた。

どう解決したか

Windows 環境から WSL の中のスクリプトを呼ぶとき、Windows 側の道しるべ（パス変換）が働く。/home/... で始まるパスが C:/Users/... に化けてしまう。WSL の中から見ると「そんなファイル、ない」になり、エラーを出さずに黙って終わる。

ここが厄介で、「動かしている」ように見えるのに「動いていない」。失敗したのに成功したように見える。記録にも痕跡が残らない。

しかも最初は「合図の指定の書き方が悪い」と信じて、2つの説を順に検証してどちらも撤回した。両方とも誤りだと確定できたのは、ちゃんと動いていた2本を同じ環境で見比べたときだけだった。「動く例」と「動かない例」を並べる——これが唯一の情報だった。

もうひとつ見落当时的罠がある。パス変換は区切り文字が/と\で違うため、/home/...はC:/に化け、C:/...はそのまま通る。1バイトずつの差だ。だから「Linuxの絶対パスなら大丈夫」と思い込んでいた。

さらに、壊れたまま放置されていた別の2点も直した。引数から操作名を取り出す処理が空白に対応していない、そして**「止めろ」の合図がexit 2という出力形式では効かない**（ブロック意思のJSON出力が必要）。テストは38本全部緑。

何が変わったか

「動かない」と言われたら、最初に疑うのは設定ではなく起動の書き方、という順序が固定された。

しかも**「測る器」が壊れている**という教訓も同時に得られた。計器が壊れていれば、壊れた計器を信じたまま原因を追い続けることになる。誤った原因が「確定」として記録されるのは、その後同じ失敗が再発する原因になる——だからだ。

「動くもの」と「動かないもの」を並べて比べる。これ1つだけで、仮説を1つ撤回できた。仮説を撤回するコストは、仮説を守るコストより安い——しかも守ろうとしたほうがよほど危険（誤原因が記録に残る）。

真因の連鎖:

Windows Desktop CC
  └─ hook コマンド: `wsl bash /home/yn4416/.claude/scripts/hooks/xxx.sh`
       └─ MSYS パス変換: /home/yn4416/... → C:/Users/yn4416/...
            └─ WSL 内で /home/... が存在しない → 静かに失敗（stderr なし・exit 0 相当）
                 └─ 発火していないように見える＝「matcher が空だから」説の誤診

撤回の根拠（対照実験）:

  • 動いていた2本= check-command-safety.py / path-rewrite.py → いずれも wsl bash -c "..." 形式
  • 動かなかった25本 → wsl bash <posix-path> 形式
  • matcher（"" / "*"）は両者に存在 → 差なし

パス変換の罠:

  • MSYS の separator 変換は / と \ で非対称
  • /home/... → C:/Users/... に化ける（壊れる）
  • C:/... → そのまま（壊れない）
  • 1バイト差（/ と \）が有无を分ける

併せて修正した独立欠陥2件（guard-destructive-commands.sh）:

  1. tool_name 抽出が空白非対応（引数の区切りが半角スペース前提）
  2. exit 2 ではブロックが効かない → {"decision":"block"} の JSON 出力が必要
